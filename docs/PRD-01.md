# PRD — Family Finance Tracker (Telegram Mini App)

Version: 1.1 (Home screen §4.1 currency-toggle behavior clarified 2026-07-19)
Status: ready for architecture/design phase

## 1. Overview

A Telegram bot + Mini App for tracking personal/family finances: income, expenses, transfers between wallets (including currency exchange UZS/USD), transaction history, and analytics. Built initially for personal use, with a data model designed to scale to multiple independent families without architectural rework.

Stack: FastAPI + Aiogram (backend), React + Vite + TelegramUI (frontend), PostgreSQL (database), monorepo structure.

Confirmed frontend tooling: linter — Oxlint (not ESLint); Telegram SDK —
`@tma.js/sdk-react` (note: the package was previously named
`@telegram-apps/sdk-react`, which is now deprecated — always install
`@tma.js/sdk-react`); state management — Zustand.

## 2. Core entities and terminology

To avoid ambiguity in later technical documents, these terms are fixed:

- **Family Budget** — the shared space one Owner and their invited Members operate in. All income/expense/transfer records and analytics belong to a Family Budget.
- **Wallet** — a place where money physically sits: e.g. "Cash UZS", "Cash USD", "Card 1", "Card 2", "Currency Card". Each wallet has exactly one currency. A card that physically holds two currencies is represented as two separate wallets (e.g. "Currency Card UZS" + "Currency Card USD").
- **User** — a Telegram user account, linked to exactly one Family Budget with a role.

## 3. User roles

| Role | Permissions |
|---|---|
| **Owner** | Full control: create/edit/delete wallets, create/edit/delete categories and subcategories, invite/remove Members, view all transactions and analytics, edit/delete any transaction |
| **Member** | Add income/expense/transfer transactions, edit/delete **only their own** transactions, view shared history and analytics, select from existing wallets/categories (cannot create or modify wallets/categories) |

Owner is created automatically on first `/start`. A Member is added via a deep-link invite generated by the Owner (see section 8).

## 4. Screens

### 4.1 Home screen
- Month selector (defaults to current month)
- **Primary currency toggle**: a `UZS`/`USD` switch that determines which
  currency's Income/Expense/Balance numbers are shown. **Updated
  2026-07-19**: unlike other per-currency data in the app (see §6), this
  toggle **fully hides** the non-selected currency's numbers within the
  Income/Expense/Balance summary block — nothing about the other currency
  is shown, not even smaller. This applies **only** to that summary
  block; it does not affect any other part of the app (History,
  Analytics, Recent Transactions — see below).
- Summary section: Income / Expense / Balance for the **currently
  selected primary currency only**. Income is shown in a
  positive/green tone, Expense in a negative/red tone, Balance in a
  neutral tone.
- Quick-action buttons: Add Income / Add Expense / Add Transfer
- "Recent transactions" block — last 3 records, **not filtered by the
  primary currency toggle** — shows the most recent transactions across
  all currencies, same as the shared History view. There is no
  currency filter anywhere in the app; the only transaction filter is by
  date (History screen's custom date range, §4.5).
- Bottom/horizontal navigation: Analytics | History | Settings

### 4.2 Add Income
Fields:
- Date & time (datetime picker, defaults to now)
- Amount (integer)
- Wallet (select — currency is inherited from the selected wallet, no separate currency field)
- Category (select, single level for income on MVP)
- Comment (textarea, optional)

### 4.3 Add Expense
Fields:
- Date & time (datetime picker)
- Amount (integer)
- Wallet (select)
- Category (select)
- Subcategory (select, dependent on chosen category)
- Comment (textarea, optional)

### 4.4 Add Transfer (generalizes currency exchange)
A Transfer moves money between two Wallets. Two sub-cases:
- **Same currency** (e.g. cash → card top-up): `from_amount == to_amount`, no rate needed
- **Different currency** (i.e. what was earlier called "exchange", e.g. UZS wallet → USD wallet): requires a rate

Fields:
- Date & time
- From wallet (select)
- To wallet (select)
- Amount (integer, in from-wallet's currency)
- Rate (integer/decimal) — shown only if from/to wallet currencies differ
- **Live calculator**: when currencies differ, the resulting amount in the target currency recalculates instantly as amount or rate is typed, in both directions (amount↔rate→result)

Rate direction convention: the entered rate always represents "how many
UZS per 1 USD", regardless of which wallet is selected as source or
target. UZS → USD: `to_amount = from_amount / rate`. USD → UZS:
`to_amount = from_amount × rate`. This keeps the rate field meaning
consistent no matter which direction the user picks.

A Transfer is **not** counted as income or expense in summaries — it only moves balance between wallets. In History it is shown with a neutral color (not red/green) and labeled "Transfer".

### 4.5 History
Table columns: date/time, amount, category (+ subcategory for expenses), comment, author (who made the entry, if there is more than one user in the Family Budget).
- Expense — red text, Income — green text, Transfer — neutral color
- Filter by period: custom date range (from – to) is required for MVP,
  in addition to a quick month selector
- No currency filter (see §4.1) — all currencies are always shown together in History, distinguished per-row by each transaction's own wallet currency.

### 4.6 Analytics
Reference: the user's own Google Sheets dashboard (categories: "Повседневные / Дом / Крупные") already implements a useful baseline. MVP chart set:
1. Expenses by category — donut/pie chart for selected period
2. Income by category — same
3. Income/Expense trend over time — bar/line chart, last 6–12 months
4. Average daily spend, spend by day-of-week (as in the reference dashboard)
5. Per-currency breakdown (total per wallet currency)

Not MVP: per-member contribution breakdown (possible in v2, no schema blocker since every transaction already stores `created_by_user_id`).

### 4.7 Settings
- Family Budget info
- **Category management** (Owner only): create, rename, delete categories/subcategories. See section 7 for delete behavior.
- **Wallet management** (Owner only): create, rename, delete wallets —
  same soft-delete logic as categories (see section 7, updated
  2026-07-11): deleting a wallet hides it from selection, existing
  transactions keep referencing it unchanged. Same open question as
  §7 applies to whether a confirmation dialog is still needed before
  hiding a wallet that has transactions.
- **Member management** (Owner only): list current members, generate invite deep-link, remove a member (see section 8)
- **Language selector** (all users, see section 9)

## 5. Categories

Two-level hierarchy: Category → Subcategory. Income categories are single-level on MVP (can extend to two-level later — schema already supports it via self-referencing `parent_id`, no migration needed to add depth).

Income and expense categories are modeled as **two separate entities**
(`income_categories`, `expense_categories`) — not a shared table with a
`type` discriminator. Wallet balance calculations sum transactions from
both entities, matched by `wallet_id`.

Seed data: the user has an existing category structure (from their spreadsheet) that will be imported as the initial seed set for expense categories — finalized during the `02-db-schema` task.

**Only the Owner can create, rename, or delete categories.** Members select from existing categories when adding a transaction; they cannot modify the category list.

## 6. Multi-currency & wallet balances

- All amounts are stored and entered as integers regardless of
  currency — including USD, which is entered as whole dollars, no
  cents.
- No forced conversion. Each transaction is stored and displayed in the currency of the wallet it belongs to.
- Underlying balances are always computed and stored per currency, never merged into one number — this avoids misleading balance swings caused by exchange rate fluctuations rather than actual money movement. **Note (2026-07-19)**: the Home screen's primary-currency toggle (§4.1) is a display-only choice about which currency's numbers appear in the Income/Expense/Balance block at any given moment — it does not change how balances are computed or stored, and no conversion between currencies ever happens anywhere in the app.
- Optional future (not MVP): an informational "≈ total in USD" line using a manually-set reference rate in Settings, clearly labeled as an estimate, purely a display feature with no effect on core balance calculation.

## 7. Category deletion logic

**Updated 2026-07-11: soft-delete, not hard-delete** (see §12 changelog). This replaces the original cascade-delete-with-confirmation design.

When the Owner deletes a category or subcategory:
1. The category (or subcategory) is soft-deleted (marked `is_deleted = true`, `deleted_at` timestamp set) — not physically removed from the database.
2. It immediately disappears from selection lists in Add Income / Add Expense and from active category management in Settings.
3. Existing transactions that reference this category are **not** touched — they keep displaying correctly in History and Analytics with the category's original name.
4. Soft-deleted categories can in principle be restored later. No restore UI is defined for MVP; this is left open for a future task if the need comes up.

**Open question (to resolve when writing Task 04 — wallets/categories API):** should deleting a category that has existing transactions still show a confirmation dialog (e.g. "N transactions use this category — hiding it won't affect their history, but it can no longer be selected for new entries"), or is soft-delete safe enough to skip confirmation entirely, since nothing is destroyed? Decide this before Task 04.

API-level note for implementation: `DELETE /categories/{id}` sets `is_deleted = true` and `deleted_at = now()`. No cascade to transactions. Whether a confirmation step / affected-count response is still needed is the open question above.

## 8. Family sharing (Members)

- Owner generates an invite via a **Telegram deep-link** (`t.me/<bot_username>?start=invite_<token>`). The invited person opens the link themselves and is added as a Member. (Phone-number-based invites were considered and rejected — Telegram Bot API cannot look up users by phone number without their explicit contact-share action, so deep-link is more reliable.)
- The Owner can **regenerate** the invite link at any time via
  `POST /api/v1/members/invite-link/regenerate`. Regeneration replaces
  `family_budgets.invite_token` with a new value — the previous link
  stops working immediately. This exists as a security measure (e.g.
  if a link was shared with the wrong person). No history of old
  tokens is kept; only the current token is valid.
- Every transaction stores `created_by_user_id`.
- Removing a Member is a **soft delete**: the Member loses access to the Family Budget, but their historical transactions remain unchanged in the database — the member record is flagged as removed, no cascade delete, no foreign key is touched. (This is the same soft-delete pattern now used consistently for categories and wallets — see §7, updated 2026-07-11.)
- No personal/private wallets for Members on MVP — all wallets are shared within the Family Budget, visible and usable by everyone in it.
- A user belongs to exactly **one** Family Budget at a time. To join a
  different Family Budget, they must first leave their current one — no
  simultaneous multi-family membership on MVP. The `role` field
  mentioned in section 10 is unrelated to Owner/Member and is reserved
  for a future platform-level admin/monetization layer.

## 9. Multi-language support

- Supported at launch: Russian (`ru`) and Uzbek Latin (`uz`).
- User selects language on first `/start`, changeable later in Settings.
- `language` stored as a plain string (ISO-like code) on the `users` table — not a database enum, to avoid a schema migration every time a language is added.
- List of supported languages lives in application config (`SUPPORTED_LANGUAGES = ["ru", "uz"]`), not in the database.
- UI strings live in per-language dictionaries (e.g. `ru.json`, `uz.json`) used via `react-i18next`. This only localizes interface chrome (labels, buttons) — user-entered data (categories, comments) is never auto-translated.
- Adding a new language later = one new JSON file + one config line, no schema changes, no code restructuring.

## 10. Non-functional requirements

- **Scalability**: relational schema with `family_budget_id` / `user_id` as mandatory foreign keys and indexes on them; no per-user database/schema separation. A `role` field already exists on `users` for a future admin panel. Primary keys are UUIDs, not serial integers (decided 2026-07-11, ahead of planned production deployment) — avoids exposing sequential record counts and simplifies merging data across environments.
- **Security**: mandatory Telegram `initData` HMAC-SHA256 validation on every API request — detailed in a dedicated `01-auth-telegram` task with exact algorithm and acceptance-criteria tests, so it does not depend on manually reading Telegram's documentation.
- **Frontend performance**: Mini App must open fast inside Telegram — React + Vite, minimal bundle, lazy-loaded Analytics screen (charts are the heaviest part).
- **Local-first for MVP**: bot and database run locally on the developer's machine; hosting/deployment is a separate, later decision and does not block development.

## 11. Out of scope for MVP

- Admin panel for managing multiple Family Budgets (schema-ready via `role` field, not built now)
- Automatic exchange rate fetching from an external source (rate is entered manually on each Transfer)
- Budgets / spending limits per category
- Report export (PDF/Excel)
- Push notifications / reminders
- Per-member analytics breakdown
- Member-specific private wallets

## 12. Resolved decisions log (for traceability)

- Multi-currency: store and display per-currency, never auto-convert core balances.
- Currency exchange = a Transfer between two wallets of different currencies (not a separate transaction type).
- Category CRUD: Owner-only. Deletion is soft-delete (updated 2026-07-11) — category hidden from selection, historical transactions unaffected, restorable in principle. Whether a confirmation dialog is still required is an open question, see §7.
- Invite mechanism: Telegram deep-link, not phone number lookup.
- Wallets vs Family Budget: "Wallet" = a place money sits (cash/card); "Family Budget" = the shared space Owner + Members operate in. These are two distinct entities.
- Members: can only edit/delete their own transactions; Owner can edit/delete any transaction.
- Documentation language: PRD, roadmap, and task files — English (better model comprehension for code-generation agents). End-user UI strings — Russian/Uzbek via i18n dictionaries. Conversation with the assistant — Russian, per user preference.
- Transfer rate is always expressed as "UZS per 1 USD" regardless of transfer direction; formula flips based on from/to currency.
- Income/expense categories: two separate entities, not a shared table with a type field.
- Wallet deletion: same soft-delete logic as category deletion (updated 2026-07-11).
- All amounts, including USD, are integers — no cents.
- Family membership is exclusive: one user, one Family Budget at a time.
- Frontend tooling confirmed: Oxlint (linter), `@tma.js/sdk-react` (correct current package — not the deprecated `@telegram-apps/sdk-react`), Zustand (state management).
- History filter: custom date range required for MVP, not just month selection.
- **Home screen primary-currency toggle (updated 2026-07-19)**: fully
  hides the non-selected currency's numbers within the Income/Expense/
  Balance summary block only (superseding the earlier "other currency
  shown smaller, never hidden" wording). Does not affect Recent
  Transactions, History, or Analytics — none of those have a currency
  filter; the only transaction filter anywhere in the app is by date.
- Invite link regeneration: Owner can invalidate the current invite
  link and generate a new one via API (added 2026-07-22, §8) — the
  invite link was previously permanent for the life of the Family
  Budget once created on Owner onboarding.
